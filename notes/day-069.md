# Day69：MCPの基本

## 目的

既存のRAG検索をMCP Toolとして公開し、特定文書の本文をMCP Resourceとして読み取る。

## 学習内容

- MCPはLLM、Tool、外部データを接続するプロトコルであり、LLMやRAGそのものではない。
- 検索Queryによって結果が変わる処理はMCP Toolで公開する。
- 特定の文書をURIで読み取る処理はMCP Resourceで公開する。
- MCPは既存RAGの検索順位を変更せず、検索機能を外部から呼び出す窓口になる。
- Toolの検索結果が不正確な場合は、MCPではなくBM25やTokenizerを切り分けて調査する。

## 成果物

- `mcp_rag_server.py`
- MCP Tool：`search_documents(query, top_k)`
- MCP Resource Template：`rag://documents/{document_id}`
- 既存の`BM25Index`と`DOCUMENTS`を再利用
- MCP InspectorでToolとResourceを確認

## 実行確認

- MCP Inspectorへの接続：成功
- `search_documents`：成功。全角数字の影響で`doc_2`が3位になる既存Tokenizer問題を確認
- `rag://documents/doc_2`：成功。`doc_2`の本文を取得
- API呼び出し：なし、費用 `0`
- MCP Python SDK `mcp==2.1.1`を依存関係へ追加

## 確認問題

- 正答率：3/3（100%）
- ToolとResourceの使い分け、検索順位の原因がTokenizerにあることを確認

## 要復習

- Toolはモデルが呼び出す実行処理、ResourceはURIで読み取るContextデータ。
- MCPを導入しても、既存RAGのTokenizerや検索品質の問題は解決しない。
