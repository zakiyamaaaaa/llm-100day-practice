# Day 66: Checkpoint・SQLite永続化・Graph再開

## 学習テーマ

Day65のLangGraphは、実行中のStateをメモリ上で扱っていた。Day66では、Graphの途中状態をCheckpointとしてSQLiteへ保存し、プロセス終了後に同じ`thread_id`で処理を再開した。

## Checkpointとは

Checkpointは、Graphのある時点におけるStateのスナップショットである。最終回答だけではなく、処理途中の`route`、`context`、`current_node`、`node_history`などを保存する。

```python
{
    "question": "様式第4号の提出先はどこですか？",
    "route": "search",
    "context": "...",
    "current_node": "retrieve",
    "node_history": ["classify", "retrieve"],
}
```

## Checkpointerと保存先

CheckpointerはCheckpointを保存・読み出しする担当である。

| 実装 | 保存場所 | プロセス終了後 | 用途 |
|---|---|---:|---|
| `InMemorySaver` | Pythonメモリ | 消える | 学習・テスト |
| `SqliteSaver` | SQLiteファイル | 残る | ローカル開発・小規模運用 |
| `PostgresSaver` | PostgreSQL | 残る | 本番運用向け |

`SqliteSaver`を使うには、LangGraph本体とは別にSQLite用パッケージを導入する必要がある。

```python
import sqlite3
from langgraph.checkpoint.sqlite import SqliteSaver

connection = sqlite3.connect(
    "agent_checkpoints.db",
    check_same_thread=False,
)
checkpointer = SqliteSaver(connection)
```

## Graphへの接続

CheckpointerはGraphのコンパイル時に登録する。

```python
graph = builder.compile(
    checkpointer=checkpointer,
)
```

`checkpointer`は保存方法をGraphへ登録するものであり、`thread_id`を渡す場所ではない。

## `thread_id`の役割

`thread_id`は、どの実行のCheckpointかを識別するキーである。同じSQLiteファイルを使っていても、異なる`thread_id`なら別のCheckpoint系列として扱われる。

```python
config = {
    "configurable": {
        "thread_id": "day66-process-resume-01",
    }
}
```

Graph実行時に`config`として渡す。

```python
graph.invoke(
    {"question": question},
    config=config,
)
```

整理すると、次の役割分担になる。

| 場所 | 指定するもの | 役割 |
|---|---|---|
| `compile()` | `checkpointer` | Stateの保存方法を登録 |
| `invoke()`の`config` | `thread_id` | 保存・再開する実行を識別 |

## 停止と再開

最初は`generate`の直前で停止するGraphを作った。

```python
pause_graph = build_graph(
    client=client,
    checkpointer=checkpointer,
    interrupt_before=["generate"],
)
```

停止時の履歴は次のようになった。

```text
current_node: retrieve
回答: None
node_history: ['classify', 'retrieve']
```

その後、プロセスを終了し、`interrupt_before`を設定していない再開用Graphを同じSQLiteと`thread_id`で作成した。

```python
resume_graph = build_graph(
    client=client,
    checkpointer=checkpointer,
)

result = resume_graph.invoke(
    None,
    config=config,
)
```

再開結果は次のとおりである。

```text
current_node: generate
回答: 様式第4号の提出先は、セキュリティチームです。
node_history: ['classify', 'retrieve', 'generate']
```

## 静的ブレークポイントの注意点

`interrupt_before=["generate"]`は、指定Nodeの直前で止める静的ブレークポイントである。停止用Graphと同じ設定のGraphで再開すると、再開時にも`generate`の直前で止まることがある。

そのため今回の検証では、次の2つを分けた。

```text
pause_graph  : generate前で停止
resume_graph : 停止条件なしで保存地点から続行
```

Day67では、ユーザー承認を待つ用途に適した動的な`interrupt()`と`Command(resume=...)`を扱う。

## Day65との違い

```text
Day65: Stateをメモリ上で管理し、Graphの経路を確認
Day66: StateをCheckpointとして保存し、プロセス終了後に再開
```

Checkpointは長期記憶そのものではない。会話単位の短期State保持や中断・復旧を担う。ユーザーの長期的な記憶設計はDay68で扱う。

## アクティブラーニング記録

```text
Checkpointの意味を確認
  ↓
InMemorySaverとSqliteSaverを比較
  ↓
checkpointerとthread_idの配置を区別
  ↓
SQLite CheckpointerをGraphへ接続
  ↓
generate前の停止を確認
  ↓
別プロセスからSQLiteのStateを復元
  ↓
generateからの再開を確認
```

## 要復習

- Checkpointは処理途中のStateのスナップショット
- `checkpointer`は`compile()`、`thread_id`は実行時の`config`に指定する
- `InMemorySaver`はプロセス終了で消えるが、`SqliteSaver`はSQLiteファイルに残る
- 同じ`thread_id`で保存済みStateを読み出す
- 静的ブレークポイントを再開用Graphにも設定すると、再び停止する場合がある
