# Day72：Ingest API

## 目的

既存のMetadata付きIngestと文書ライフサイクル処理をFastAPIから呼び出し、文書の新規登録・重複排除・更新をAPIの結果として確認する。

## 学習内容

- APIへはサーバー上の`path`ではなく、`source`と`content`を渡す。
- `path`を外部入力にすると、任意ファイル参照やパス移動の危険がある。
- `source`は`.txt`のファイル名だけに制限し、`../`や別ディレクトリを受け付けない。
- `content`は空本文や極端に長い本文をEmbedding前に拒否する。
- `section`を見出しへ変換し、既存のMetadata付きChunkingを再利用する。
- Content Hashで文書内容の変更を検出する。
- 同じHashなら`unchanged`、本文が変われば古いChunkを削除して`updated`にする。

## 成果物

- `rag_api.py`へ`POST /ingest`を追加
- `IngestRequest`：`source`、`content`、`section`を検証
- `IngestResponse`：`status`、`source`、`chunk_count`を返す
- Day51の`sync_file`、`build_versioned_chunks`、Chroma Collectionを再利用

## Ingestの状態

```text
初回登録       → inserted
同じ本文を再登録 → unchanged
本文を変更     → updated
```

更新時に古いChunkを削除しないと、更新前の情報と更新後の情報が同時に検索対象となる。LLMが古いChunkを参照し、現在の正しい情報ではない回答を生成する危険がある。

## 実行確認

登録した文書：`manual.txt`

```text
1回目：status=inserted、chunk_count=1
2回目：status=unchanged、chunk_count=1
本文変更後：status=updated、chunk_count=1
```

入力検証と同期処理はEmbedding・Vector DB登録より前後の適切な境界で実行される。OpenAI Embedding APIを使用したため、費用は未確認。

## 注意点

Day72では登録APIの境界とライフサイクルを確認した。`/query`の検索Contextへ新しい文書を動的に反映する結合処理は、Day79で扱う。

## 確認問題

- 正答率：4/5（80%）
- 補足説明後の理解：100%
- 新規登録・冪等性・更新・古いChunk削除の必要性を確認

## 要復習

- `inserted`は新規文書、`updated`は同じsourceの内容変更、`unchanged`は同じContent Hashを表す。
- Ingest APIの入力検証と、RAG検索時の未回答判定は別の責務。
- 古いChunkを残すと、RAGが過去情報を根拠として使う可能性がある。
