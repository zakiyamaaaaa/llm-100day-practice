# Day 52: Query Rewrite

## 学習テーマ

検索に失敗したQueryを、文書検索に適した表現へRewriteし、Rewrite前後のBM25検索結果を比較した。

## 学習した内容

- Query Rewriteは回答生成ではなく、検索用Queryを作る処理である。
- ユーザーの質問をLLMへ渡し、文書タイトルに近い検索語へ変換する。
- Rewrite後のQueryをBM25へ渡すことで、表記揺れやToken不一致による検索失敗を改善できる。
- `allowed_vocabulary`は、実際の文書タイトルをLLMへ参考情報として渡す仕組みである。
- `allowed_vocabulary`により、LLMが存在しない申請書名や部署名を勝手に作るリスクを減らせる。
- 現在の実装では、`allowed_vocabulary`は厳密な制約ではなく、Promptによるソフトな制約である。
- Query Rewriteが元の質問から離れる可能性があるため、元のQueryを残し、Rewrite前後を評価する必要がある。
- 未回答ケースをRewriteすると、存在しない文書へ無理に誘導する危険がある。
- 実務では、元Query、Rewrite Query、言い換えQueryを複数検索し、Vector検索・RRF・Rerankerと組み合わせる。

## 処理の流れ

```text
ユーザー質問
    ↓
LLMによるQuery Rewrite
    ↓
Rewrite後Query
    ↓
BM25 / Vector検索
    ↓
検索結果の評価
```

例えば、次のQueryをRewriteした。

```text
元の質問: 機密情報を扱う申請書の提出先は？
Rewrite後: 機密情報取扱申請書 提出先
```

## 実行結果

| ケース | Rewrite前 | Rewrite後 |
|---|:---:|:---:|
| `confidential_information` | False | True |
| `travel_expense` | False | True |

Rewrite対象2件が、Rewrite後はどちらも正解文書を取得できた。

```text
confidential_information → doc_1
travel_expense → doc_3
```

## 確認問題と回答

初回問題:

1. `confidential_information`がRewrite後に検索できた理由: 文書表現に近い「機密情報取扱申請書 提出先」へ言い換えたため。正解。
2. `allowed_vocabulary`を渡す目的: 未回答。解説後に再出題。
3. Query Rewriteだけに頼る危険: 元の文章とかけ離れ、意図しない検索になる可能性がある。正解。

追加問題:

1. `allowed_vocabulary`で防ぐ誤り: LLMが文書に存在しない申請書名や部署名を勝手に作らないよう、実際の文書タイトルを参考情報として渡す。正解。

## 要復習

- `allowed_vocabulary`は現在のコードでは厳密なAllowlistではなく、LLMへの参考情報・Prompt上のソフトな制約である。
- Query Rewriteは検索用Queryを作る処理であり、回答を生成する処理ではない。
- 元Queryを残し、Rewriteによる検索改善と意図ずれを評価する。
