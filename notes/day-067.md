# Day 67: Human-in-the-Loop

## 学習テーマ

Day66のCheckpoint・再開を活用し、LLMが提案した副作用のあるToolを、人間の承認なしに実行しない仕組みを実装した。

今回は実際の文書やDBは変更せず、実行内容を返すモックの`write_document` Toolを使用した。

## Human-in-the-Loopの役割

```text
LLM       : Tool実行案を作る
Graph     : 承認Nodeへ処理を進める
人間      : approve / edit / rejectを決める
Python    : 決定後に検証済みToolを実行する
```

今回のコードでは、LLMは「承認が必要か」を判断していない。`propose_write`の後に必ず`approval`へ進むGraph構造によって、承認を必須にした。

## Graphの構造

```text
START
  ↓
propose_write
  ↓
approval
  ├─ approve → execute_write → END
  ├─ edit    → execute_write → END
  └─ reject  → reject → END
```

## LLMによるTool提案

`propose_write`では、ユーザーの依頼をLLMへ渡し、Structured OutputでTool名と引数を取得する。

```python
class WriteProposal(BaseModel):
    tool_name: Literal["write_document"]
    arguments: WriteDocumentArguments
```

LLMはToolを実行せず、次のような実行案だけを返す。

```python
{
    "tool_name": "write_document",
    "arguments": {
        "document_id": "doc_2",
        "content": "更新後の本文",
    },
}
```

## approval Node

`approval`では、`interrupt()`でTool実行前にGraphを停止する。

```python
decision = interrupt(
    {
        "question": "このToolを実行してよいですか？",
        "tool_name": state["tool_name"],
        "arguments": state["tool_arguments"],
    }
)
```

再開時には、同じ`thread_id`を使い、`Command(resume=...)`で判断を渡す。

```python
graph.invoke(
    Command(resume={"decision": "approve"}),
    config=config,
)
```

## 3つの判断

- `approve`: LLMの提案どおりに実行
- `edit`: 人間が修正した引数で実行
- `reject`: Toolを実行せず、拒否理由を保存して終了

`edit`では、修正後の引数をStateへ保存してから`execute_write`へ進む。

## 承認後の防御

承認後も、Day59のTool Registryを再利用している。

```text
承認
  ↓
Tool Allowlist確認
  ↓
Pydantic引数検証
  ↓
Tool実行
```

承認と技術的な安全検証は別の防御層である。承認された引数でも、Allowlistと型検証を通す。

## interruptの注意点

副作用のある処理は`interrupt()`より前に置かない。

```python
# 危険
write_to_database()
decision = interrupt("承認しますか？")
```

再開時にNodeが先頭から再実行されると、書き込みが二重実行される可能性がある。

安全な順番は次である。

```python
decision = interrupt("承認しますか？")

if decision == "approve":
    write_to_database()
```

## 実行結果

### approve

```text
node_history: ['propose_write', 'approval', 'execute_write']
human_decision: approve
tool_result.status: success
```

### reject

```text
node_history: ['propose_write', 'approval', 'reject']
human_decision: reject
tool_result.status: rejected
```

`execute_write`を通っていないため、書き込みToolは実行されていない。

### edit

```text
node_history: ['propose_write', 'approval', 'execute_write']
human_decision: edit
tool_result.status: success
content: 修正後の本文です。
```

人間が修正した引数でToolが実行された。

## Day66との関係

```text
Day66: Checkpointで途中Stateを保存し、再開する
Day67: 保存された承認待ちStateを、人間の判断後に再開する
```

Human-in-the-Loopには、Checkpointerと同じ`thread_id`が必要である。承認待ちのStateを保存し、後から同じ実行を再開するためである。

## アクティブラーニング記録

```text
副作用のあるToolに承認が必要な理由を説明
  ↓
reject時にToolが実行されないことを予測
  ↓
interrupt()の配置場所を判断
  ↓
thread_idとCheckpointの関係を確認
  ↓
Command(resume=...)の内容を記述
  ↓
approve・reject・editの3経路を実行
  ↓
LLMの役割をTool実行案の作成として整理
```

## 問題結果

- アクティブ課題数: 8問（再確認を含む）
- 初回正答率: 87.5%
- 最終理解率: 100%
- 実行確認: approve・edit・rejectの3経路すべて成功

## 要復習

- LLMはTool実行案を作るが、今回の承認要否はGraphで固定している
- 人間の判断は`approve`・`edit`・`reject`
- `reject`では副作用のあるToolを実行しない
- `edit`では修正後の引数を検証してから実行する
- 承認後もAllowlistとPydantic検証を行う
- 副作用は`interrupt()`より後に置く
