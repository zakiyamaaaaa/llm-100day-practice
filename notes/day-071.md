# Day71：RAGをFastAPIで公開する

## 目的

既存のProduction RAGをHTTP APIから利用できるようにし、入力不正・回答不能・正常回答を別の結果として扱う。

## 学習内容

- FastAPIはLLMそのものではなく、RAG/Agentを外部アプリへ公開する接続口。
- `/health`はアプリの起動確認であり、RAGやLLM APIを呼び出さない。
- `/query`は既存のBM25、Vector、RRF、Reranker、Context、LLM回答を呼び出す。
- API入力はPydanticで検証し、空白だけの質問や範囲外の`top_k`をRAG実行前に拒否する。
- 入力が正常でも回答根拠がない場合は、APIエラーではなく`HTTP 200`と`status="refused"`で返す。
- 入力値が不正な場合は、`HTTP 422 Unprocessable Entity`で返す。

## 成果物

- `rag_api.py`
- `answer_with_citations.py`の候補数受け渡し対応
- `productioin_rag_v1.py`のAPIからの候補数受け渡し対応
- `pyproject.toml`へFastAPI・Uvicornを追加

## API契約

正常回答：

```json
{
  "status": "answered",
  "answer": "様式第4号の提出先は、セキュリティチームです。",
  "sources": ["doc_2"],
  "refusal_reason": null
}
```

根拠がない場合：

```json
{
  "status": "refused",
  "answer": null,
  "sources": [],
  "refusal_reason": "経費精算の締め日についての情報が参考情報に含まれていないため。"
}
```

## 実行確認

- `GET /health`：成功。`{"status":"ok"}`を確認
- 回答可能な質問：`status="answered"`、`sources=["doc_2"]`を確認
- 回答根拠がない質問：`HTTP 200`、`status="refused"`、`sources=[]`を確認
- 空白の質問と`top_k=0`：`HTTP 422`を確認
- OpenAI API：`/query`で使用。費用は未確認

## 重要な理解

```text
入力不正              → HTTP 422
入力正常・文書なし    → HTTP 200 + refused
入力正常・文書あり    → HTTP 200 + answered
```

HTTPステータスは通信・入力処理の結果を表し、`status`はLLM/RAG上の回答状態を表す。

## 確認問題

- 初回正答率：4/7（57%）
- 補足説明と実行確認後の理解：100%

## 要復習

- APIエラーと、LLMアプリの業務上の未回答を混同しない。
- `/health`の成功だけでは、RAG PipelineやLLM APIの正常性は保証されない。
- 入力検証をRAGより前に置くことで、不要な検索・Embedding・LLM呼び出しを防ぐ。
