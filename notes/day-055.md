# Day 55: Context Builder

## 学習テーマ

RRF・Rerankerの検索結果から、回答生成用のContextを作成した。
Context Builderで重複除去、関連度順の並び替え、Token上限の確認を行い、LLMへ渡す文書を制御する。

## Context Builderの役割

```text
BM25・Vector検索
        ↓
RRF
        ↓
Reranker
        ↓
Context Builder
  ├─ 重複除去
  ├─ 関連度順に並び替え
  ├─ Token上限を確認
  └─ 回答生成用Contextを作成
        ↓
回答生成LLM
```

RetrieverやRerankerの結果をすべてLLMへ渡すと、無関係な文書、余分な入力Token、Context Window超過のリスクが発生する。
Context Builderは、回答生成に使う文書を最終的に選ぶ責務を持つ。

## 実装した処理

### 1. 関連度順への並び替え

Rerankerの`relevance_score`が高い文書から処理する。
同じスコアの場合は`document_id`を第2条件にして、順位を安定させる。

### 2. 重複除去

`seen_document_ids`という集合を使い、同じ文書IDをContextへ複数回追加しない。

### 3. Context形式への変換

各文書を次の形式へ変換する。

```text
[source: doc_3]
title: 出張経費事前申請書
text: 出張経費事前申請書（様式第9号）の提出先は、総務部経費精算係です。
```

`source`を含めることで、回答の引用元を追跡し、後続のCitation処理へ渡せる。

### 4. Token上限の確認

今回のコードでは、モデル用Tokenizerである`tiktoken`を使ってContextのToken数を計測した。
文書を追加したContext全体が上限を超える場合、その文書を途中で切らず、文書単位で除外する。

## 実行結果

```text
[Context Builder結果]
採用文書: ['doc_3']
除外文書: ['doc_1', 'doc_2']
使用Token数: 50

[LLMへ渡すContext]
[source: doc_3]
title: 出張経費事前申請書
text: 出張経費事前申請書（様式第9号）の提出先は、総務部経費精算係です。
```

`doc_3`を追加した時点で使用Token数が50になった。
設定した上限が60だったため、`doc_1`と`doc_2`を追加すると上限を超え、除外された。
これは文書単体が大きすぎるという意味ではなく、採用済みContextへ追加した場合の合計が上限を超えるという意味である。

## Context Windowとアプリ側の上限

モデルのContext Windowは、モデルが1回のリクエストで扱える入力・出力全体の上限である。
一方、アプリ側のContext上限は、その中からシステムプロンプト、質問、Tool・Schema定義、会話履歴、回答用の予約Token、安全余白などを差し引いて決める。

```text
アプリ側Context上限
= min(
    モデルContext Window
    - 固定Prompt
    - 質問
    - Tool・Schema・履歴
    - 回答用予約Token
    - 安全余白,
    アプリ側の実用上限
)
```

今回の`max_tokens=60`は、除外動作を確認するための学習用の固定値である。
実務では、モデルごとのContext Windowを設定で管理し、入力内容を`tiktoken`で計測して動的にContext予算を決める。

また、`max_tokens`という名前はAPIの出力Token設定と混同しやすいため、実務では`max_context_tokens`のような名前が分かりやすい。

## 確認問題と回答

1. `doc_1`と`doc_2`が除外された主な理由は何ですか？
   - 回答: `doc_3`から追加で読み込む際に、設定しているToken上限を超えてしまうため。
   - 判定: 正解。採用済みContextへ追加した場合の合計Token数が上限を超えるため除外された。

2. Contextに`source: doc_3`を含める目的は何ですか？
   - 回答: 回答の引用元を追跡するための情報。
   - 判定: 正解。引用やCitation評価で根拠文書を特定するために使う。

3. モデルのContext Windowと、アプリ側のContext上限は何が違いますか？
   - 回答: モデルのContext Windowはモデルで把握できるContextの範囲、アプリ側はReranker後にLLMに渡せるContextの上限。
   - 判定: 正解。Context Windowは入力・出力全体のモデル上限で、アプリ側の上限はPrompt・質問・回答用Tokenなどを考慮して設定する実用上の文書Context上限である。

## 要復習

- Rerankerは順位を決め、Context BuilderはLLMへ実際に渡す文書を最終決定する。
- Context BuilderのToken上限は文書単体ではなく、採用済みContextとの合計で判定する。
- Context Window全体を文書Contextに使わず、回答用Tokenと安全余白を確保する。
- `source`や`document_id`をContextに残すことで、後続の引用処理へつなげられる。
