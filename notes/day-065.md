# Day 65: LangGraphによる最小Graph

## 学習テーマ

既存のLLM分類・RAG検索・回答生成処理を、LangGraphのNodeとEdgeで接続した。
目的は、LangGraphを使うとLLMの回答精度が自動的に上がることではなく、Agentの実行状態と処理経路を明確に管理できることを理解すること。

## 今回の成果物

`agent_langgraph_minimal.py`

既存処理を再利用し、次の処理をLangGraphのGraphとして構成した。

```text
START
  ↓
classify
  ├─ route="search"      → retrieve
  │                            ├─ contextあり    → generate → END
  │                            └─ contextなし    → fallback → END
  └─ route="unsupported" → fallback → END
```

## LLM/AI固有の処理

単なるPythonの条件分岐ではなく、次の既存処理をGraphへ組み込んだ。

- `classify_question`: LLMに質問を分類させ、Structured Outputの`route`と`reason`を取得する
- `retrieve_context`: RAG検索で質問に関連するContextを取得する
- `generate_answer`: 検索Contextを根拠に、LLMに最終回答を生成させる
- `fallback_node`: Contextがない場合に、LLMへ推測させず回答を拒否する

特に、`classify_question`と`generate_answer`は役割が異なる。

- 分類: 次に進む処理を決めるためのLLM呼び出し
- 生成: 検索後のContextを使ってユーザー向け回答を作るLLM呼び出し

## State・Node・Edge

- State: Node間で受け渡す`question`、`route`、`context`、`answer`などの状態
- Node: Stateを読み取り、更新内容を返す1つの処理
- Edge: Stateの内容を見て、次に実行するNodeを決める経路
- `END`: Graphの終了地点。処理Nodeではないため、`node_history`には記録しない

Nodeは次のNode名を直接返すのではなく、Stateの更新内容を返す。次のNodeを決める責務はConditional Edge側にある。

## node_history

`current_node`は最後に実行したNodeだけを示す。一方、`node_history`は実行した全Nodeを順番に記録する。

```python
state.get("node_history", []) + ["retrieve"]
```

これは、既存の履歴を残したまま、現在のNode名を末尾に追加する処理である。

実行結果:

```text
検索成功: ['classify', 'retrieve', 'generate']
未対応質問: ['classify', 'fallback']
```

この履歴により、Agentがどの処理をどの順番で通ったかを確認できる。デバッグ、監視、処理経路の説明に利用でき、ポートフォリオ上も「出力結果」だけでなく「Agentワークフローを設計した証拠」になる。

## Frameworkの使い分け

### 手書き状態機械

分岐やNode数が少なく、処理経路が固定的な場合は、手書き実装で十分である。依存関係が少なく、処理の理解もしやすい。

### LangGraph

Query Rewriteのループ、再検索、リトライ、チェックポイント、複数の分岐など、状態遷移が複雑になった場合に有効である。LangGraphはNodeの処理内容を自動で改善するのではなく、State・Node・Edgeを管理する。

### Agents SDK

Tool実行やAgent間の委譲、実行ループ、Guardrailなど、Agent実行そのものを扱う場合に検討する。LangGraphと目的が重なる部分はあるが、同じものではない。

## アクティブラーニング記録

完成コードを最初から写経せず、次の順番で確認した。

```text
既存のRAG処理の再利用箇所を特定
  ↓
LangGraphのState・Node・Edgeを予測
  ↓
条件分岐の経路を予測
  ↓
node_historyの追加処理を実装
  ↓
実行結果で2つの経路を確認
  ↓
LLM分類処理と回答生成処理の役割を区別
```

再確認後、次の点を説明できるようになった。

- `classify_question`が質問分類を担当すること
- `generate_answer`がContextを使った回答生成を担当すること
- `route="search"`のときの経路が`classify → retrieve → generate`であること
- 検索結果がない場合の経路が`classify → retrieve → fallback`であること
- `node_history`がAgentの実行経路を記録すること

## 問題結果

- アクティブ課題数: 21問（再確認問題を含む）
- 最終正答率: 100%
- 実行確認: 2ケース、2経路とも成功

## 要復習

- `current_node`は最後のNode、`node_history`は全Nodeの履歴
- NodeはState更新を返し、Edgeが次のNodeを決める
- LangGraphは検索精度を自動改善するものではなく、複雑な状態遷移を管理するもの
- `classify_question`と`generate_answer`の役割を混同しない
