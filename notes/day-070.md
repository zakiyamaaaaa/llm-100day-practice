# Day70：Agent v1演習

## 目的

Day59〜69で作成した安全対策とMCP/RAG部品を、1つのAgent実行に統合し、処理経路を監査ログで追跡できるようにする。

## 統合した部品

- `search_documents`：Day69のMCP Toolを直接再利用
- `ToolRegistry`：許可されたToolだけを実行し、引数を検証
- RAG検索：BM25で候補文書を検索
- Resource取得：検索1位の文書本文を取得
- 実行予算：`max_tool_calls`でTool呼び出し回数を制限
- 監査ログ：`thread_id`、`node`、`event`、`tool_name`、`status`、`detail`を記録

## 成果物

- `agent_v1_demo.py`

このDayでは、LLMによる回答生成、Checkpoint、Human-in-the-Loopを再実装していない。これらはDay58、Day66、Day67で作成・確認したため、Day70では既存部品を統合することに集中した。

## 実行確認

質問「様式第4号の提出先はどこですか？」に対して、次の処理を確認した。

```text
plan → retrieve → context → answer
```

- `search_documents`の実行回数：1回
- 検索結果の1位：`doc_2`
- Resourceから`doc_2`本文を取得
- 回答に`[source: doc_2]`を付与
- 監査ログにTool実行とResource取得を記録
- OpenAI API呼び出し：なし、費用：0

## 重要な理解

- `tool_name`は、`search_documents`や`write_document`など、実行対象のToolを区別するための監査情報。
- MCP Resourceの読み込みはTool実行ではないため、`tool_name`は`None`になる。
- Resource取得は`event=resource_read`と`detail`で記録する。
- Day70の目的は新しい検索アルゴリズムの実装ではなく、既存の安全部品を接続してAgent v1として動かすこと。

## 確認問題

- 正答率：50%→100%
- ToolとResourceの監査ログ上の違い、既存部品統合の目的を確認

## 要復習

- `tool_name`はToolの識別情報、`event`は処理イベントの種類を表す。
- `tool_name`などの項目名は設計上の命名であり、重要なのは意味と一貫性。
